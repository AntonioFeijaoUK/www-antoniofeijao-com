# Enforcing Custom DNS on Debian 12 Raspberry Pi with NetworkManager

## Introduction

On modern Debian-based systems, particularly **Raspberry Pi headless setups**, managing DNS can be deceptively complex.

The traditional `/etc/resolv.conf` file is often dynamically managed by **NetworkManager** or **systemd-resolved**, making persistent custom DNS configurations non-trivial.

In this guide, we explore a reliable approach to enforce specific DNS servers across multiple interfaces, with a focus on **NextDNS**, a privacy-focused, high-performance DNS provider.

---

## TL;DR

- **Problem:** `/etc/resolv.conf` being overwritten by DHCP or NetworkManager, causing unpredictable DNS resolution.  
- **Solution:** Use **connection-level DNS configuration in NetworkManager** for persistence.  
- **Outcome:** DNS is enforced across all interfaces, survives reboots, and benefits from NextDNS privacy and security features.

## Detailed Technical Steps

### 1. Initial State

The default resolv.conf looked like this:

```bash
# Generated by NetworkManager
nameserver <internal_IP>
```

Attempts to configure DNS via `/etc/dhcp/dhclient.conf` or a `99-dns.conf` global file were ineffective because:

NetworkManager ignores unknown config sections such as `[global-dns]`.

DHCP can inject DNS unless explicitly disabled per connection.

### 2. Identifying Active Connections

Using `nmcli device status` confirmed that NetworkManager was managing both `eth0` and `wlan0`:

```bash
nmcli device status
```

This distinction is crucial: device-level modifications are runtime-only, while connection-level modifications persist across reboots.

### 3. Enforcing Persistent DNS per Connection

We configured both connections to ignore DHCP-provided DNS and use custom NextDNS servers:

```bash
nmcli connection modify "Wired connection 1" ipv4.ignore-auto-dns yes
nmcli connection modify "Wired connection 1" ipv4.dns "<MyNextDNS_IP1> <MyNextDNS_IP2>"

nmcli connection modify "preconfigured" ipv4.ignore-auto-dns yes
nmcli connection modify "preconfigured" ipv4.dns "<MyNextDNS_IP2> <MyNextDNS_IP1>"
```

`ipv4.ignore-auto-dns yes` prevents DHCP from injecting unwanted DNS entries.

DNS entries are specified in the order of preference.

### 4. Reactivating Connections

To apply the changes immediately:


```bash
nmcli connection down "Wired connection 1" && nmcli connection up "Wired connection 1"
nmcli connection down "preconfigured" && nmcli connection up "preconfigured"
```

After this step, `/etc/resolv.conf` reflected only the specified NextDNS servers:

```bash
# Generated by NetworkManager
nameserver <MyNextDNS_IP1>
nameserver <MyNextDNS_IP2>
```

### 5. Cleaning Up Ineffective Configs

Any previously created global configuration files were removed:

```bash
rm /etc/NetworkManager/conf.d/99-dns.conf
sudo systemctl restart NetworkManager.service
```

NetworkManager now relies solely on connection-level DNS settings.

This ensures no conflicts or duplicate entries appear, even with multiple active interfaces.

### 6. Benefits of Using NextDNS

[NextDNS](https://nextdns.io/?antoniofeijao.com) provides several advantages over traditional DNS providers:

**Privacy**: Blocks trackers, telemetry, and malicious domains.

**Security**: Provides DNS-level protection against malware and phishing.

**Performance**: NextDNS maintains a high-performance global network, reducing DNS latency.

**Customisation**: Allows filtering, logging, and analytics per device or connection.

By enforcing NextDNS servers on both Ethernet and Wi-Fi interfaces, the Raspberry Pi benefits from consistent, secure, and private DNS resolution, regardless of network changes or DHCP behaviour.

### 7. Lessons Learned

`Device-level` vs. `connection-level` DNS: Runtime-only vs. persistent configuration.

Global config files in `/etc/NetworkManager/conf.d/` cannot enforce DNS unless they follow supported directives.

DHCP must be explicitly ignored to prevent unwanted DNS injection.

Reactivation of connections is required for changes to take effect immediately.

### 8. Conclusion

For headless `Debian 12` systems using `NetworkManager`, the best approach is:

Identify all NetworkManager-managed interfaces.

Apply connection-level DNS settings.

Ignore DHCP-provided DNS to enforce consistency.

Verify `/etc/resolv.conf` after reactivating connections.

This method ensures stable, private, and high-performance DNS resolution using NextDNS, regardless of interface changes or system reboots.
